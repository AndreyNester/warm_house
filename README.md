### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователь может:
  - включать и выключать отопление в помещении X дома Y (при наличии прав);
  - задавать желаемую температуру для помещения/зоны;
  - настраивать расписание обогрева (дни недели, временные интервалы, температура);
  - временно переопределять расписание (повысить/понизить температуру до определённого времени).
- Система должна:
  - на основе расписания, текущих настроек и показаний датчиков включать/выключать отопление;
  - контролировать допустимый диапазон температур.

**Мониторинг температуры:**

- Пользователь может:
  - просматривать текущую температуру в помещении X;
  - просматривать список помещений/зон и их температуру;
  - просматривать историю температур за период.
- Администратор может:
  - выполнять CRUD-операции над датчиками (добавление, изменение параметров, деактивация);
  - просматривать список всех датчиков и их состояние.
- Система должна:
  - периодически собирать показания датчиков;
  - хранить историю измерений и предоставлять её по запросу;
  - отслеживать выход температуры за заданные пороги (для уведомлений).

**Ведение учета склада:**

- Сотрудник склада может:
  - регистрировать новые единицы инвентаря (датчики, контроллеры, инструменты);
  - изменять состояние инвентаря (на складе, зарезервирован, установлен, списан);
  - просматривать остатки оборудования.

**Платежи:**

- Клиент может:
  - просматривать свои начисления и статус оплат;
  - оплачивать услуги (картой, СБП и т.п.).
- Система должна:
  - формировать платёжные запросы во внешний платёжный шлюз;
  - обрабатывать уведомления об успешных/неуспешных платежах;
  - обновлять статусы оплат.

### 2. Анализ архитектуры монолитного приложения

**Используемый стек технологий**

- Приложение написано на Go (Golang).
- Использует фреймворк Gin для реализации HTTP API.
- База данных: PostgreSQL (взаимодействие через собственный пакет db).
- Приложение подключается напрямую, без ORM.
- База служит для хранения информации о сенсорах.

**Архитектурный стиль**

- Монолит
- Приложение собрано в один бинарный сервис, который:

1. обслуживает HTTP API,
2. выполняет бизнес-логику,
3. обращается к БД,
4. вызывает внешние сервисы.

- Синхронная модель
- Все взаимодействия между компонентами происходят через синхронные вызовы (HTTP → внешний API → DB → response).
- Нет очередей сообщений, событийного обмена, брокеров сообщений.
- Tightly Coupled
- Компоненты сильно связаны:

HTTP API вызывает сервис

сервис вызывает внешний API температуры

сервис читает и модифицирует записи в базе

Ошибка одного компонента напрямую ломает остальные.

**Особенности логики приложения**
Live Update при каждом GET

- Когда выполняется запрос к /sensors или /sensors/:id:

приложение читает сенсоры из БД

если сенсор температурный — отправляет HTTP-запрос в внешний сервис

результат подменяет поля Value, Status, LastUpdated

Это создаёт:

сильную зависимость от внешнего API

потенциальные проблемы производительности (N запросов на N сенсоров)

отсутствие кеширования

**Развёртывание**

- Docker
- Приложение запускается в контейнере:

app — основной монолит

postgres — база данных

temperature-api (опционально)

Сервисы общаются через Docker bridge network.

### **4. Проблемы монолитного решения**

**Ограничения текущего монолита (As-Is)**

- Невозможно масштабировать частями — всё в одном сервисе.
- Сильная связь с БД и внешним API — ошибки мгновенно ломают API.
- Нет самообслуживания устройств — пользователи не могут сами подключать датчики .
- Отсутствуют модули освещения, ворот, наблюдения — только отопление.
- Нет событийной архитектуры — устройство не может отправлять данные в систему.
- Нет механизма для партнёрских устройств — всё жёстко прошито.

Если вы считаете, что текущее решение не вызывает проблем, аргументируйте свою позицию.

Вам нужно:

1. сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**
- Пользователь может:
  - Включать и выключать отопление в помещении X дома Y (при наличии прав)
  - Задавать желаемую температуру для помещения/зоны
  - Настраивать расписание обогрева (дни недели, временные интервалы, температура)
  - Временно переопределять расписание (повысить/понизить температуру до определённого времени)
- Система должна:
  - На основе расписания, текущих настроек и показаний датчиков включать/выключать отопление
  - Контролировать допустимый диапазон температур

**Мониторинг температуры:**
- Пользователь может:
  - Просматривать текущую температуру в помещении X
  - Просматривать список помещений/зон и их температуру
  - Просматривать историю температур за период
- Администратор может:
  - Выполнять CRUD-операции над датчиками (добавление, изменение параметров, деактивация)
  - Просматривать список всех датчиков и их состояние
- Система должна:
  - Периодически собирать показания датчиков
  - Хранить историю измерений и предоставлять её по запросу
  - Отслеживать выход температуры за заданные пороги (для уведомлений)

**Ведение учета склада:**
- Сотрудник склада может:
  - Регистрировать новые единицы инвентаря (датчики, контроллеры, инструменты)
  - Изменять состояние инвентаря (на складе, зарезервирован, установлен, списан)
  - Просматривать остатки оборудования

**Платежи:**
- Клиент может:
  - Просматривать свои начисления и статус оплат
  - Оплачивать услуги (картой, СБП и т.п.)
- Система должна:
  - Формировать платёжные запросы во внешний платёжный шлюз
  - Обрабатывать уведомления об успешных/неуспешных платежах
  - Обновлять статусы оплат

### 2. Анализ архитектуры монолитного приложения

**Используемый стек технологий**
- Приложение написано на Go (Golang)
- Использует фреймворк Gin для реализации HTTP API
- База данных: PostgreSQL (взаимодействие через собственный пакет db)
- Приложение подключается напрямую, без ORM
- База служит для хранения информации о сенсорах

**Архитектурный стиль**
- **Монолит** - приложение собрано в один бинарный сервис
- **Синхронная модель** - все взаимодействия через синхронные вызовы
- **Tightly Coupled** - компоненты сильно связаны

**Особенности логики приложения**
- Live Update при каждом GET запросе
- Сильная зависимость от внешнего API
- Потенциальные проблемы производительности
- Отсутствие кеширования

**Развёртывание**
- Docker контейнеры: app, postgres, temperature-api
- Сервисы общаются через Docker bridge network

### 3. Определение доменов и границы контекстов

**Микроклимат / Управление домом (Core domain)**
- Управление отоплением
- Мониторинг температуры

**Обслуживание клиентов (Supporting)**
- Логистика и саппорт (заявки, выезды)

**Учет склада и оборудования (Supporting / Generic)**
- Ведение склада, инвентарь, оборудование

**Биллинг и платежи (Supporting)**
- Начисления, счета, интеграция с платёжным шлюзом

**Технические / общие вещи (Generic)**
- Identity & Access (пользователи, роли, дома, права)
- Логи

### 4. Проблемы монолитного решения

**Ограничения текущего монолита (As-Is)**
- Невозможно масштабировать частями — всё в одном сервисе
- Сильная связь с БД и внешним API — ошибки мгновенно ломают API
- Нет самообслуживания устройств
- Отсутствуют модули освещения, ворот, наблюдения
- Нет событийной архитектуры
- Нет механизма для партнёрских устройств
